## The adversarial asks (find what the gates CANNOT see)

1. **The two-commit pause protocol's failure windows.** Between commit 1 (window + action) and commit 2 (pause event): a control/resume/report can land (CAS retry replays the mutate on fresh state). Does the second commit's mutate (`apply(cur2, pauseEv)` + queues rewritten unchanged) behave correctly when: (a) a RESUME control was enqueued in between (applied after the pause? consumed?); (b) the window aged out between commits (the pause still mints — correct?); (c) commit 2 CAS-conflicts repeatedly (the turn's budget dies mid-ladder — what's the state?). Read conductor/turn.mjs's pause block + store.commit's retry semantics.
2. **The trigger's re-fire loop.** With the window-presence gate: a FAILED alert → re-trigger every tick → the adapter retries the alert each tick — is there ANY shape where this loops forever WITHOUT aging out (clock skew? ts minting? the window's ts source)? What happens to the journal growth rate (one BUDGET_PAUSE_ALERT action per tick — journaled or not?).
3. **The rollover's rebuild parity.** The ROLLOVER journals as CONTROL reset with genesisSpec — replay rebuilds the intake epoch. Verify: rebuild(journal) after a rollover tick reconstructs project.issue, the task-i<N> task, the config adoption — and that a PAUSE-then-ROLLOVER sequence (the epoch completes while paused? can it?) can't produce a paused fresh epoch that never dispatches.
4. **The door's trust boundary.** Any path from a hostile issue body to: the run-name regex (law-4), the dispatch prompt (assembleDispatchPayload's untrusted() neutralizer vs the door's validated fields), the write-back door's pathspec (artifacts bound to minted id — the `..` fold), or the queue line's shape (the store's parse)? Think: re-opened EDITED body (new sha8 → new queue line — two lines same issue), a spec whose `id` collides with an ACTIVE epoch's task id (task-exists at TASK_CREATED? the rollover embeds directly — what happens?), 4KB of hostile unicode.
5. **The spent-aware budget arithmetic.** The fn contract `(spent) => slots`: the clock passes passAssigns, conductorTick adds tick-wide ASSIGN counts from journals. Can the count double-count (an ASSIGN journal from a PRIOR apply in the same tick counted twice?) or miss (ASSIGNs minted by the wake apply after the last fn call)? What's the worst case — over- or under-assign?
6. **Pruning vs the live epoch.** A pruned record loses history/lease/spec — any consumer that reads those fields on a terminal task? (The adapter's intake completion comment reads last_result — on PRUNED? The REPORT drain's reject paths? recount? The law-4 scan's tasks map?) Find every reader.
7. **Test honesty.** Mutation-check 3 pins of your choosing: break the code (e.g. remove the window-presence gate's `.length`, swap the backstop's `!countTrigger`, drop the STOP_CHAIN filter) and confirm the SPECIFIC pin fails (name it). A pin that survives its mutation is a lie.
8. **The workflow YAML.** intake.yml: any secrets.*? The permissions block minimal? Does `issues: [opened, reopened]` wake on PRs (it must NOT)? The concurrency group's interaction with the conductor's.
